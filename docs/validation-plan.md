# 判定の精度を上げるための検証データ

公開の骨格検知モデル（MediaPipe）で関節の位置は取れる。
しかし、スマホ1台で横から撮った映像から「フォームの崩れ」を正確にとらえるところまでは届いていない。
原因は、このアプリが判定したいこと（この走りはここが崩れている）の**正解が付いたデータが世の中にない**こと。

## 方針

- 骨格検知のモデルはそのまま使う。自前で学習させるのではなく、関節の角度から「崩れ」と判定する**しきい値の調整**を中心にする。
- しきい値の調整なら大量のデータは要らない。**数十本の動画**でかなり進む。目安は5〜10人で、体格・性別・走力をばらけさせる。
- 届くのは、はっきりした猫背やオーバーストライドを捕まえられるところまで。疲れて少しずつ出る小さな崩れは、もっと多くの人数と本数が要る。

## コーチに見せる前の自分での確認

- わざと崩すと声が出る
- ふつうに走って声が出すぎない
- スマホの置き方を少しずらしても結果が変わらない
- 30分動かして落ちない

## 自宅のトレッドミルでの「答えつき」の記録

走るのは1回、線を直すのは何回でも。走る日は、Mac の声で区間ごとに崩し方を指示し、どの時刻に何を崩したかが分かる記録を取る。
走らない日に、その記録を今の判定にもう一度通して採点し、線を変えては採点し直す。

- 走る：横の iPhone でカメラ版を、URL に `?full=1` を付けて開いて始め（全コマ記録。ホームの「はじめる」の下と、走っている画面に「全コマ記録」と出る。置き方と立った姿勢の基準まで済ませる）、腰のスマホでスマホ版を「トレッドミル」で始めてから、Mac で `npm run drill`。
  既定は全体約31分：歩き7分（時速5.0）→ 止めて、合図でジャンプ1回 → ジョグ20分（時速8.0。ふつう4分 → 「崩し30秒 → ふつうに戻す30秒」を8回 → 残りはふつう）→ 歩き3分。
  崩しは真横のカメラで見える上半身のものが中心で、脚に負担の大きい崩し（弾む・かかとから前に・べた足）は既定に入れていない（`--steps` で足せる）。
  先に `npm run drill -- --dry-run` で時刻表を、`npm run drill -- --try` で声を確かめられる。区間の表と長さ・速さのオプションは `scripts/treadmill-drill.mjs` の先頭
- 記録：`~/Developer/research-data/runs/drill-YYYYMMDD-HHMM.json`。区間の始まり（言い終えた時刻）と終わりを、Mac の時計のエポックミリ秒で残す。言うたびに書き直すので、Ctrl+C で止めてもそこまでは残る
- 採点：`npm run logs` で記録を取ってきてから、`npm run grade -- <drill-….json> <rfc-….json> [<rfc-phone-….json>]`。
  区間ごとに、崩しを見つけたか・区間の始まりから最初の声までの秒数・ふつうの区間の誤った声・戻しの区間で声が止まったかを、
  「そのとき（記録にある声）」「いまの線（今のコードに通し直した声）」「上書き（`--set head=7` などで線を変えた声）」の3つ並べて出す。
  カメラ版は、しくみが走り始めた時刻と、走り始めの自分の基準を作った間（どの区間か）とその値も出す。歩きや崩しの区間が入っていたら、その基準では採点の数字を信じない。
  通し直しの確かめ（そのときの声が、撮ったときと同じ条件で通し直して出るか）は、いつも記録の始めから撮ったときの項目で通したものと比べる。
  `--running steps` で、カメラ版の「走っている」を歩数だけで決め直せる（その場で走るフリの見分けを切ったとき）
- 通し直しの限り：カメラ版は、ふだん（`?full=1` なし）は撮ったときに骨格を取ったコマ（安定して走っている間は10秒のうち3秒）だけが記録にあり、線を下げて「もっと細かく見たはず」になった秒は足せない。
  全コマ記録（`?full=1`）なら走っている間の毎コマ（毎秒15コマまで）があり、毎コマで通し直す。`--thin` を付けると、同じ記録をふだんの間引きに通し直し、間引いたときに声が遅れる・抜けるかを比べられる。
  30分ぶんで約3万行、JSON で約11MB、送るとき（gzip）は約4MB（送り先の上限は64MB）。電池と熱のため、ふだんの走りでは付けない。
  スマホ版は届いたコマすべてが残っているので、ほぼ撮ったときのとおりに通せる（記録の値の丸めで、線の際の秒がまれに変わる）
- 時計：iPhone・スマホ・Mac は、どれも時刻を自動で合わせている前提。ジャンプの「はい」から、記録で大きく動き始めるまでの秒数を採点の表に出す（ふつうは 0.3〜0.8 秒）。大きくずれていたら `--camera-offset` / `--phone-offset` で直す。
  合図の前に跳んでしまうと、その動きを拾って前にずれて出る。直す前に、崩しの区間の始まりで角度が変わった時刻（頭を前に出した時刻など）とも合っているか確かめる
- 採点の見本：`node scripts/treadmill/make-sample.mjs <フォルダ> [--full]` で、区間の記録と作りもののカメラ版・スマホ版の記録を作る（採点の道具を試すためだけのもの。線の根拠にはしない）

## 動画の集め方

- **撮り方はアプリと同じにそろえる**: 三脚に固定したスマホで、トレッドミルを真横から撮る。高さと距離もそろえる。
- **走る人は正しいフォームでなくてよい**: 普通のランナーのクセがそのまま、よくある崩れの材料になる。
- **わざと崩してもらう必要はない**: 少し疲れるまで（20〜30分）いつも通り走ってもらえば、後半に自然に崩れる。これはアプリが捕まえたい「後半の崩れ」そのもの。
  判定は、その人自身の直立姿勢や走り始めと比べて行う（全員が正しいフォームである必要はない）。
- わざと崩した動画（下を見る・背中を丸めるなど）は、判定が鳴るかの確認用に本人が数本撮れば足りる。

## 正解の付け方

- **コーチが走りを見ながら話した言葉を、同じ動画に録音する**。何秒のところで何が崩れているかが、そのまま正解になる。
- 数字で測れるもの（体幹の傾き、着地のすねの角度、上下動）は、研究の目安（見本に使っている Fukuchi 2017 のデータなど）と比べて判定する。
- 見た目で決めるもの（猫背など）は、コーチに一部を見てもらって基準をそろえる。

## 検証の仕方

- **基準を決めるのに使う人と、精度を確かめるのに使う人を分ける**（例：7人でしきい値を決め、残り3人で当たるかを確かめる）。
  同じ人の動画で調整と確認の両方をすると、精度が実際より高く見える。

## ネットにある走る動画

使えるのは次の確認までにとどめる。

- 判定が明らかな崩れ（「悪い例」の動画）に反応するか。逆に、きれいなフォームで鳴りすぎないか。
- 体格・服装・肌の色・明るさが違っても、骨格検知が崩れないか。

しきい値を決める材料には使わない。理由は次のとおり。

- 撮り方が違う（屋外、カメラが追いかける、斜め、編集やスロー）ので、角度の数値がずれる。
- わざとの崩れは大げさで、どこから鳴らすかの基準が決められない。
- どの瞬間がどう悪いかが分からず、結局自分で印を付けることになる。
- YouTube の利用規約は動画のダウンロードを原則禁止している。著作権法30条の4は解析のための利用を広く認めているが、映っている人の肖像の問題もある。製品にするときは、どのデータで作ったか説明できる状態にしておく。

## 次にやること

- **水戸ランナー塾に相談する**: 参加者に走ってもらい、コーチにその場で見て話してもらう撮影の場を作れないか。
  - トレッドミルの持ち込みは重い（家庭用でも50〜100kg）。参加者に市のジムに来てもらう、短期レンタルする、なども考える。
  - 最初は大人だけにする（キッズ部門の子どもは保護者の同意が要り、ハードルが上がる）。
  - 同意書を1枚用意する：アプリの検証に使う、外には公開しない、求められたら削除する。
  - 紹介動画とアプリの URL を見せて反応を見てから、何を一緒にやるかを決める流れの中で、この撮影を提案する。
