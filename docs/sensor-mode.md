# センサーモード（センサーだけで走るモードは仕様だけ。いまはカメラ版といっしょに使う）

体に付けたセンサーで走りを見て、崩れを**振動**で知らせて直すモード（声は補助。判断のしくみはカメラモードと共通）。
トレッドミルのカメラモードが本線で、センサーモードはその2本目の使い方。

## 誰のためか

- 路上やトラックで走る、本気でタイムを縮めたいランナー・トライアスリート
- コーチに見てもらえるのは一瞬で、1人で走ると自分が見えない。動画を後で見ても、走っている最中には分からない。この穴を埋める
- カメラが届かない場所なので、ここではセンサーが要る

## 2つのモード

声かけのしくみ（`src/core/engine.ts`）は共通にし、入り口と、見る項目の一覧だけをモードごとに替える。
カメラモードの項目は減らさない。カメラモードは「全身が見えるので、より高度な判定ができる」扱い。
センサーにしか測れない項目もあるので、「それぞれ得意な項目がある」と見せる。

| 項目 | カメラモード | センサーモード | センサーでの測り方（案） |
|---|---|---|---|
| 首（頭が前に出る） | ◎ | ◎ | 頭のセンサーの前への傾き（いまある。下を向いたのとは分けられない） |
| 上体の前傾 | ◎ | ◎ | 胸のセンサーの前への傾き（いまあるのは猫背） |
| 体全体の前傾（足首→肩の線） | ◎ | ― | |
| 腰の落ち込み | ◎ | ― | 腰にセンサーがないので測らない |
| 腕振り | ― | ◎ | 手首のセンサーの前後の振れ幅 |
| 接地時間（腰が落ちる） | ― | ◎ | 両足首のジャイロで1歩ごとに着地・離地を見つけ、接地の割合を速さごとの市民ランナーの線と比べる（いまある） |
| 左右差 | ― | ◎ | 両足首の接地時間の左右差（いまある）。歩の間隔の左右差は、2つのセンサーの時計を合わせられないので見ない |
| 着地の衝撃 | ― | ○ | 足首のセンサーの、接地の瞬間の加速度（記録だけ。付け方で値が変わるので知らせない） |

## センサー

自作する（構成は別メモ。XIAO nRF52840 ＋ LSM6DSV、1個約3,250円）。

- 付ける場所：両手首、両足首、首（首の付け根の後ろ側）、胸（心拍計の胸ベルト）の6か所
- 無線：BLE でスマホに直接送る。XIAO nRF52840 の技適（211-220207）の範囲で使う。SlimeVR の Smol Slime の独自無線（ESB）は技適の面でグレーなので使わない
- 送るもの：センサーごとに、時刻・向き（クォータニオン）・加速度。1秒に送る回数は試して決める（姿勢だけなら数十回、着地の衝撃には数百回要る）
- 6個の時刻をそろえる方法は、作りながら決める

## 知らせ方：振動

崩れたら、声ではなくノードを振動させる（2026-10-15 に決めた。声は「言われた」感が残りイラっとすることがある。振動は何も言わずに気づかせられ、イヤホンも要らない）。
判断は、できるだけ下の層に置く。詳しくは `hardware/sensor/docs/haptic.md`。

| 層 | 置くもの |
|---|---|
| センサーチップ（LSM6DSV16X の FSM / MLC） | 1ノードで決まる反射：着地、着地の強さ、ケイデンスの低下、腕振りの周期、「いつもの走り／崩れた走り」の2値分類 |
| XIAO | 振動のパルス、ケイデンス誘導（実際の着地に位相を合わせて 2% 速く叩く）、絶対の姿勢（SFLP）、ルールの受け取り |
| スマホ | ノード間の比較（首と胸の角度差、左右差）、ルールを作って配る、記録。`engine.ts` の「いつ知らせるか・直ったらほめる・だんだん減らす」はそのまま使い、出口を声から振動に替える |

- まず手首1個で、感じ取れるかを確かめてから広げる（走行中の振動の実績があるのは手首。足首は未確認）
- 「言葉で書いたルール（例：着地が外に流れたら右足首を叩く）をノードに流す」は、XIAO が解釈する JSON ルールから始める

## いまあるもの：カメラ版といっしょに使う（`src/modes/sensor/`）

トレッドミルのカメラ版で走りながら、自作のセンサーもつなげる。カメラの判定と声はそのままで、センサーは胸で猫背を、頭で頭が前に出たのを見てその場所を震わせ、値を記録に残す。
外ではカメラがないので、センサーの判定はセンサーだけで決める（カメラから受け取るのは、立った姿勢を取る時刻と「走っている」だけ）。カメラは、線を決めるための答えに使う。

- つなぎ方：ホームの「はじめる」の下の「センサーをつなぐ」で、場所ごとに「つなぐ」を押して名前を選ぶ（Web Bluetooth。ブラウザの決まりで1個ずつ、押したときだけ）。一度選んだものは、`getDevices` があるブラウザなら次から押さずにつなぐ。走っている途中で切れたら、押さずに3回までつなぎ直す
- iPhone の Safari は Web Bluetooth がないので、つなげない（枠に Bluefy で開くよう出す）。センサーなしでも、カメラ版はそのまま使える
- 付ける場所とセンサーの対応は `params.ts` の `SLOTS` だけで決める（今は 頭=1、胸=2、左手首=4、左足首=3、右足首=6、右手首は空き。手首はカメラ（左から撮る）に見える左に付ける）
- 崩れの見分け（`lean.ts` の `LeanDetector`、数字は `params.ts` の `HUNCH`（胸）と `HEAD`（頭）。胸と頭は同じしくみで、線だけ違う）：
  - 立った姿勢：カメラが直立の基準を取った3秒の、そのセンサーの加速度の平均の向き
  - 走る前傾：カメラが歩数で「走っている」とみた時間で、走り出して10秒あとからの30秒。この間に立った姿勢から傾いた向きの平均を「前」とし、前への傾き（符号つき）の真ん中の値を走る前傾にする（胸はふつうの走りで 約12〜16°、頭は 約1〜15°）。横に傾いた・後ろに反ったのでは増えない
  - 基準：走る前傾から始め、線の下にいる間だけ時定数60秒で今の傾きへゆっくり寄せる。ベルトの上でセンサーが少しずつずれていくのを吸うため（2026-11-02 20:23 の走りで、胸の傾きが3分半で約15°増えたのに、カメラの上体は 2〜8° のまま。寄せないと2分すぎから胸が鳴り続けた）。線を越えている間は寄せないので、崩れたままなら知らせ続ける
  - 走っている間、前への傾きが基準 + margin を1.5秒続けて超えたら、その場所を1秒震わせ、超えたままなら4秒ごとに震わせ直す。線の下に戻れば止まる
  - margin：頭 18°。胸はランナーのレベルごと（`HUNCH_BY_LEVEL`：初心者 6°・中級 5.5°・上級 5°。レベルが分からなければ中級）。カメラが「背中が丸まっています」と言うときに胸も震えるよう、カメラの猫背の線（`STRICT` の hunch）に寄せた。
    2026-11-04 の走りで、前の 8° ではカメラの猫背の声3回（胸の値がある間）に1回しか震えず、5〜6° で2回。ふつうの区間の外れは10分あたり 1.4 → 2.2〜2.7回（`sim/result-chest-camera.md`、くわしくは `docs/validation-plan.md`）
  - 立った姿勢は、カメラの直立の確かめ（決まった線。猫背なら背筋を伸ばして測り直す）を通った3秒で覚える。測り直しを使い切ったときは、その3秒
  - 寄せることの代わり：ゆっくり進む崩れは吸ってしまう。胸で +12° の猫背なら約50秒、+15° なら約75秒、+20° なら約2分より時間をかけて進むと鳴らない（数秒〜数十秒で丸まるのは鳴る）
  - ずれの見張り（`slipSec`・`slipDecay`・`slipDrift`）：次のどちらかで、崩れではなくセンサーの付け位置がずれたとみなし、基準を直近10秒の傾きの真ん中の値へ置き直す。その場所を短く3回（0.3秒×3）震わせ、記録の events に `sensor:slip 胸 18.2→34.6`（ずれを測るもとの基準 → 置き直した基準）を残す。走っている間は画面を見られないので、走ったあとの結果の画面に「胸のセンサーが13分ごろにずれたようです。次は付け直してください」と出す（記録の `slips`・`head.slips` から、走り出してからの分。`slipText.ts`・`SlipNote.tsx`）。声は出さない
    - 線を越えていた時間（線の下にいる間は同じ速さで減らす）が75秒に達した：急にずれて、線を越えたままになったとき。寄せる基準は線の下でしか動かないので、これがないと走り終わるまで4秒ごとに鳴る
    - 寄せた基準が、走る前傾（前にずれとみなしたときは、そのときの基準）から前へ 胸 8°・頭 15° 動いた：少しずつずれたとき（寄せて吸っているので知らせる回数は変わらないが、付け直しを促す）。後ろへ動いたのは見ない（鳴りにくくなるだけ）
    - 仮想実験（`sim/lean-slip.sim.ts`、結果は `sim/result-lean-slip.md`。揺れは 2026-11-03 15:08 の胸に合わせた）：胸 +13° のわざとの猫背 40秒・60秒・60秒×2（間60秒）は、20通りのどれもずれとみなさず、見張りなしと同じ回数（60秒で約15回。3つのレベルとも）知らせる。急に +13° ずれると、見張りなしで約136回のところ約19回（約75秒）で黙る。上級（5°）は、+13° を5分かけてゆっくりずれると、ずれとみなす（約510秒）までに約16回鳴る（初心者 6° では0回）。頭は線が広く、+22° のずれでも線のすぐ上を出入りするだけで、もともと鳴り続けはしない
    - 見張りの代わり：75秒より長く崩れたままだと、ずれとみなして黙り、基準が崩れた形に寄る（胸で 90秒の猫背なら20通りのうち19回）。戻ったあと基準が下がるまでの1〜2分は、鳴りにくい
    - 走り出してすぐの短いずれ（15:08 の 225〜240秒、+9° が10秒ほど。そのあと +3〜4° 上で落ち着いた）は、短い猫背と分けられないので鳴る
  - 頭のセンサーは、首が前に出たのと下を向いた（うなずいた）のを同じに見る（カメラの顎の角度と r −0.97）
  - 体を曲げた（物を拾う・靴ひもを結ぶ。`bend`・`bendAfter`・`confirmAbove`・`confirmSec`）：胸の傾きが基準 +45° 以上なら走る姿勢ではないとみなし、胸も頭も知らせない。
    曲げている間と戻ってから5秒は、基準も寄せず、ずれの見張りにも数えない（越え始めてからの分もなかったことにする）。events に `sensor:bend 胸 <傾き>`、記録の `bends` に残す。
    頭は曲げるより先に下を向くので、大きく傾いて知らせるとき（胸 基準 +20°・頭 +35° 以上）は1秒待ち、その間に胸で曲げたと分かれば知らせない
    - 決め方：2026-11-04 の走りで物を拾った3回（22・27・35分ごろ）は、胸が基準 +82〜84°（立った姿勢から 76〜92°）、頭が +53〜59°。走っている間の胸の「傾き − 基準」は
      4本の記録で、ふつう上から0.1%で +12〜19°、わざとの猫背（11-03）で +36°。頭はわざと前に出したテストでも +47〜50° あり、頭だけでは曲げたのと分けられない
    - 確かめ（`npm run replay:sensor -- <記録> --gate stop`。アプリと同じく、立ち止まった数秒も走っているとみる）：11-04 の3回の胸と頭の知らせ（アプリと同じ時刻に出る）が6回とも消え、
      ほかの知らせは変わらない。4本で、ほかに曲げたとみなしたところはない。代わりに、頭の知らせが 11-02 20:23 で 13 → 12回（4秒あけて続けて鳴ったものが1回になる）、ほかにも 0.4〜2秒遅れるものがある（越えたままの知らせ直しは待たない）
    - 胸のセンサーがないと、頭だけでは曲げたのが分からない（1秒待つだけで、知らせる）
  - カメラの今日の基準（整えたあとの形）は走り出して3分以上たってからできるので、センサーの走る前傾はそれを待たない
- 確かめた結果（`npm run replay:sensor` に記録を通した。数字は3本の走りと Mac のテストだけから）：
  - 胸：20:23 の走り（上体はずっとまっすぐ）で、寄せる前は16回（約44回/10分）鳴ったのが3回（約8回/10分。そのうち2回はカメラの上体も数秒で +4〜5° 動いたところ）。わざと猫背にしたテスト（Mac、40秒）は寄せても同じく9回、ふつう・胸を張っては0〜1回
  - 胸のずれの見張り：2026-11-03 15:08 の走り（20分。胸のセンサーが 715秒ごろからずれ、傾きが +12° 前後のまま。カメラの上体は 3〜6°）で、知らせたのは見張りの前後とも20回（715秒からあとは 720・730・804・849・926秒の5回）、ずれとみなしたのは 851秒（基準 18.2° → 34.6°。いまの線（中級 5.5°・上級 5°）では約795秒で、それまでの約80秒に鳴る回数が増える）。この走りでは、ずれのあとの傾きが線のすぐ上を出入りし、線の下に入るたびに基準が寄っていたので、もともと鳴り続けてはいなかった（アプリの記録の cues でも 715秒からあとは5回：720・724・730・849・927秒）。わざとの猫背（405〜465秒）は前後とも6回鳴る。20:23 の走りは 500秒でずれとみなす（回数は3回のまま）。18:43 はずれとみなさない
  - 頭：カメラの答え（`FORM.head`：首 > 48° かつ 頭の位置 > 52°）と5秒の窓で比べて、18:43 は一致 98%（崩れを見つけた 89%）、20:23 は一致 88%（100%）。首が 40° 未満（はっきり崩れでない）のときに鳴らしたのは2本で1回。margin 14 なら見つける割合は上がるが外れが増え、20 なら外れはなくなるが 18:43 の崩れの2割を見逃す
- 記録：走った記録（`RunLog` の `sensors`）に、センサーの値をセンサーごとに約1秒ずつ base64 で入れる（形は `core/types.ts` の `SensorLog`、戻すのは `log.ts` の `decodeBlock`、場所ごとの速さは `nodeHz`）。
  速さは場所ごと（`SENSOR_LOG.rates`）：足首 50Hz（そのまま）、頭・胸・手首 25Hz（4件の平均）。5か所で約12MB/時（前の 5か所 × 50Hz は約17MB/時で、約35分の上限で切れていた）。上限は置かず、7時間（マラソン）でも最後まで残す。
  1秒ごとのまとめ `sec`（`secCols`：走っているか・胸と頭の傾きと基準・曲げているか・接地の割合・左右の接地時間・速さ・ピッチ）、電池の電圧 `bat`（60秒ごと）、体を曲げた `bends` も入る。
  走っている間は60秒ごとに端末へ書き出し（`core/logChunks.ts`。手元に溜めないので、アプリが落ちてもそこまでは残る）、送るときは2時間ごとのファイルに分けて、`npm run logs` がつなぐ。胸と頭それぞれの立った姿勢・走る前傾・知らせた時刻と傾き（胸はいちばん上の `stand`・`runLean`・`cues`、頭は `head` の中。頭を見る前の記録には `head` がない）、センサーごとの抜けと電池も入る。ずれとみなした記録は、胸はいちばん上の `slips`、頭は `head.slips`（[t, もとの基準, 置き直した基準]。見張る前の記録にはない）。カメラの記録の events には `sensor:stand`・`sensor:runLean`・`sensor:hunch`（胸）と `sensor:headStand`・`sensor:headLean`・`sensor:head`（頭）、`sensor:slip <場所>` が残る。時刻はカメラの記録と同じ時計（`rows` の t）

## 接地時間と左右差（足首の2つ。`contact.ts`・`contactCoach.ts`、数字は `params.ts` の `STEP`・`CONTACT`）

- 見つけ方（`StepDetector`）：足首（すね）のジャイロの、前後の面の回転の速さを使う。振り出しの大きな山のあと、0 を下へ切ってから 26ms で着地。次の振り出しの前に 0 を上へ切る、その前 0.25秒の谷から 90ms 前が離地。軸はジャイロの主成分（付け方の向きは決めない）、符号は両方の向きで1歩を探して、もっともらしい1歩が多いほう。時刻はセンサーの時計で数える（Bluetooth の遅れが入らない）
  - ずらす量は RBDS（Fukuchi 2017、床反力つき。読めた22人）の印から作ったすねの角速度で決めた。同じデータで、接地時間のずれは1歩ずつ ±18〜21ms、人・足ごとの真ん中の値で 2 ± 17ms、取りこぼし 0〜1%（100Hz と、記録の 50Hz でほぼ同じ。`sim/result-contact.md`）。印から作った値なので皮膚や衝撃の揺れは入らず、実機の足首のセンサーを床反力と比べた答えは、まだない
- 接地が長い（腰が落ちている）：線は今日の走り出しではなく、研究データの市民ランナー。接地の割合（接地時間 ÷ 1歩き）は速さで変わるので、すねの振れ幅 ÷ 1歩きの時間から速さを見積もり、その速さの平均 + 2 × 標準偏差（Patoz ら 2022、115人：時速9km 37.7 ± 3.1%、11km 34.7 ± 2.5%、13km 32.6 ± 2.2%。表の外は端の値）を越えたら知らせる。RBDS の22人は、床反力の本当の値で誰も越えない
  - 接地の割合が高い人は、接地の間に脚を深く曲げる（Patoz ら 2020）。ただ、接地が長いのは腰が落ちたときだけではない（大また・かかとからの着地でも長くなる。11-03 の「足を前に出す」1分で、接地の割合は z 2.1 まで上がった）。高い接地の割合はそういう走り方の型でもあり、効率は変わらないという研究もある（Lussiana ら 2019）ので、線は外れた人だけに当たる高さにした
- 左右差：接地時間の |右 − 左| ÷ 平均 が 15% を越えたら、長いほうの足首を震わせる（20秒の窓）。RBDS の床反力では、どの人も 10% 未満（いちばん大きくて 9.3%）、Garmin の「左右のバランス」でも 52.2% を越える（左右差 約9%）のは上から5%。付け方が左右で違うと接地時間にも見かけの差が出るので、振り出しの山が左右で 1.25 倍より違えば左右差は見ない
  - 着地の衝撃の左右差は記録だけ（付け方・50Hz の間引きで値が大きく変わる。4本とも右が 1〜3割重かったが、本当の差か付け方かは分けられない）。歩の間隔（左 → 右と右 → 左）の左右差は、2つのセンサーの時計の差を数 ms まで合わせられない（10ms ずれると見かけで約5%）ので見ない
- 知らせ方：声かけのしくみ（`engine.ts` の `CueEngine`）をそのまま使う（6秒の平均が線を越えたら知らせ、同じ項目は30秒あけ、直ったらほめ、だんだん減らす）。腰は両足首、左右差は長いほうの足首を1秒震わせ、直ったら同じ場所を短く2回。カメラ版で走っている間は声も出す（「腰が落ちています…」はカメラと同じ言葉、「右足の接地が長くなっています…」、直ったら「いい感じです」「左右がそろいました」）。カメラの声と重ならないよう、声が出ている間は振動だけ
- 知らせない間：走り出して30秒・見積もった速さが20秒の間に1割より変わった・ピッチが1割より変わった間は知らせない（線より下の値は渡すので、直ったかは見る）。歩き（接地の割合 > 0.5）の1歩は捨てる
- 記録：camera の記録の events に `sensor:contact sit 2.1`（知らせた。値は平均から標準偏差いくつぶん上か、左右差なら %）、`sensor:contactOk`（ほめた）、30秒ごとの `sensor:steps df … ct … L … R … v … cad … imp …`
- 自分の記録（`sim/result-contact.md` の③）：接地時間は 264〜295ms、接地の割合 0.37〜0.39（時速9km の市民ランナーの平均くらい）。4本・判定した54分で知らせは2回（10分あたり 0.4回。どちらも 11-04）：1486秒の左右差（左が 17% 長い。この走りは左が 8% 長いのがふつうで、ほかの3本は左右差 2% 以内）と、2240秒の腰（カメラが「足が体より前に着いています」と言ったあとで、ピッチが 164 → 147 に落ちた区間）
- まだ確かめていないこと：わざと腰を落とした走りで知らせるか（記録がない）、足首の振動を走りながら感じ取れるか、見積もった速さがベルトの速さと合うか（RBDS では ±1.1km/h。実機ではベルトの速さの記録がない）

## 今の入力との対応

`coach.ts` の入力（`CoachInput`）は、センサーからも作れる。

| 入力 | カメラモード | センサーモード |
|---|---|---|
| `present`（人がいるか） | 骨格が映っているか | センサーがつながっているか |
| `moving`（走っているか） | 脚の動き | 足首のセンサーで数えた歩数 |
| `m`（角度） | 骨格の点から（`geometry.ts`） | センサーの向きから（新しく作る） |
| `frame`（骨格33点） | 渡す | 渡さない。走り姿のアニメーションはカメラモードだけの機能 |

## 判定の基準

カメラモードと同じ考え方を使う。

- 走る前に、まっすぐ立って3秒止まる（今の直立の基準）。センサーモードでは、各センサーが体のどの向きに付いているかの補正も、このときに取る
- 上体などは、走り始めの自分の平均からの増え方で判定する（今の `REL_LIMITS` の考え方）

## コードでやること（作り込みのとき）

1. センサーから角度を作る入り口を作る
2. `coach.ts` の見る項目の一覧（今は `ITEMS` に4つ固定）を、モードごとに渡す形にする。項目を足すときは、線（`params.ts`）と声かけの言葉（`phrases.ts`）を足す
3. 人に配るときは、Bluefy に頼らず iPhone で Bluetooth を読めるよう、今のウェブアプリを iPhone アプリの殻（Capacitor など）に包む。App Store で配れる形にもなる
4. 1ノードで決まる反射はルールにしてノードへ送り、スマホからは「今この部位を1回叩く」だけを送る（案）。叩く入り口（0xFFE3 の書き込み）は `ble.ts` の `buzz` にある

## 試し方

- 自作のセンサーが動くかは、Mac の Chrome（Web Bluetooth）で、今のウェブアプリのまま確かめられる。iPhone では Bluefy（Web Bluetooth に対応したブラウザ）で開く。iPhone の Safari は Web Bluetooth に対応していない
- 自分の iPhone で試すだけなら App Store の審査は要らない（Xcode から入れる）
- トレッドミルでカメラとセンサーを同時に使い、カメラの角度を答えにしてセンサーの角度を確かめる（下の「カメラに合わせる」）

## カメラに合わせる（`npm run compare:sensor`）

外ではカメラがないので、センサーだけの判定の線は、トレッドミルでカメラといっしょに走った記録で、カメラの骨格の判定に合うように決める。カメラ版は `?full=1`（全コマ記録）で走る。

- 使い方：`npm run compare:sensor -- <rfc-….json>`（ファイル名だけなら `RFC_RUNS_DIR` から読む）。`--win 秒`（まとめる窓、既定5秒）、`--json 出力.json`（決めた線と一致率。リポジトリの外に書く）
- 中身は `scripts/compare-sensor-camera.mjs`（計算は `scripts/sensor-camera.mjs`、テストは `scripts/sensor-camera.test.ts`）。ブロックの戻し方（`decodeBlock`）・カメラの線（`camera/params.ts` の `FORM`）・着地の山（`camera/landing.ts`）は src のものをそのまま使う
- 時刻：ブロックの t は届いた時刻で、Bluetooth の遅れがばらつく。センサーの時刻（ms）で並べ、前後15秒でいちばん遅れの少なかったブロックに合わせる
- 見る区間：カメラの段階が run で、歩数で走っていたコマ（5秒より短い区間は除く）。立った姿勢は、カメラが直立の基準を取った間（`phase:baseline` → `phase:run`）
- 出すもの：センサーごとの取れ方（切れ目・`sensor:` のできごと）、頭（頭の傾き と 首の角度・頭の位置・顎）、胸（胸の傾き と 上体）、ピッチ（足首の自己相関 と カメラ）、着地（足首の衝撃の山の左右差、カメラの着地の山との時刻・左右）、腕振り（手首のジャイロ と カメラの手首の振れ幅）
- 崩れの答えは、カメラの `FORM` の線で窓ごとに付け、センサーの傾きでいちばんよく分かれる線と一致率（見つけた割合・外れなかった割合・AUC）を出す。線の案は画面に出すだけで、`params.ts` には書かない（人が決める）。1本の走りの数十窓から出した数字なので、何本かで確かめてから入れる
- 立った姿勢は、アプリが覚えたとき（記録の `stand`、頭は `head.stand`）の直前3秒で取る（アプリと同じ）。`stand` がない記録だけ、カメラの直立の基準の間全部を使う（直立の前に体を動かしていると、向きがずれる）
- アプリの知らせ方そのもの（前の向き・基準の寄せ方・線・続ける長さ）は、`npm run replay:sensor -- <rfc-….json | Mac の記録のフォルダ> …` で記録を流し直して確かめる（`scripts/replay-sensor.mjs`）。知らせた回数・10分あたり・知らせたときのカメラの値・ずれとみなした時刻・5秒の窓の一致率を出す。走っているかは、カメラの行のいちばん近い前の行で決める。カメラは走っている間、骨格を間引いて取る（行のない間が7〜17秒）が、アプリはその間も前の判定のまま「走っている」とするので、20秒までの行のない間は前の行のままにする（そうしないと、間引いている間は走っていないことになり、基準が寄らず、知らせた回数がアプリの記録と合わない）。`--chest '{"follow":0}'` のように数字を上書きして試せる（`params.ts` は変えない）。Mac の記録（`hardware/sensor/records/…`）は区切りごとの回数を出す
- 真横から撮るので、奥の腕は骨格がほとんど取れない。腕振りは、見えるほうの手首で比べる（左右の腕は逆に同じ大きさで振る、とみなす）

## まだ決めていないこと

- 6個が本当に要るか。胸・腰・両足首の4個で足りるなら、そのほうが付けるのも買うのも楽
- 腰のセンサーを足すか（腰の落ち込みと上下動が測れるようになる）
- 各項目の線（どこから振動させるか）
- どの崩れをどの場所の振動で知らせるか（崩れた部位のノードを鳴らすか、いつも手首か）
- スマホに6個を BLE で同時につないで安定するか
